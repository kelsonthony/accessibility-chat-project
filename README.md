## 1. Overview

**AccessChat** is a conversational assistant specialized in the major digital accessibility standards — WCAG 2.1, LBI (Brazil), ADA, Section 508, and EN 301 549. It does not use mocked responses: every answer is generated by a **RAG (Retrieval-Augmented Generation)** pipeline that retrieves relevant chunks from a vector knowledge base before calling the LLM.

The real differentiator, however, is the **telemetry engine**: the app silently observes how users interact with the chat and sends behavioral events in batches to the backend — valuable data for training AI models, detecting hesitation patterns, measuring perceived latency, and understanding how people with different accessibility needs navigate the interface.

## 4. Technical Decisions

### Database: PostgreSQL + pgvector

**Why PostgreSQL instead of a dedicated vector store (Pinecone, Weaviate)?**

For this project's scope, PostgreSQL with the `pgvector` extension offers the best cost-to-benefit ratio: a single instance manages users, telemetry, sessions, documents, and embeddings. This eliminates the operational complexity of a second service and preserves ACID transactions between related entities (e.g. ensuring a `document_chunk` is only queryable after its parent `document` is committed).

At scale, pgvector supports HNSW and IVFFlat indexes for efficient approximate nearest-neighbor search across millions of vectors — sufficient for the accessibility knowledge base.

> **Compatibility note:** The Oracle Cloud PostgreSQL instance does not have `pgvector` installed. In that environment, embeddings are stored as `jsonb` and similarity search is performed in memory using dot product. For full production use, install pgvector with: `CREATE EXTENSION IF NOT EXISTS vector;`

### RAG instead of mocked responses

The RAG pipeline was chosen for three reasons:

1. **Grounded responses** — the LLM only answers based on chunks retrieved from real standards (WCAG 2.1, LBI, ADA, Section 508, EN 301 549), reducing hallucinations.
2. **Traceability** — every response includes `sources` with title and section, so users can verify the origin.
3. **Business relevance** — Hand Talk's core is accessibility; a system that cites real standards is more honest and useful than generic responses.

Ranking uses a **BM25 + cosine similarity** hybrid to balance lexical and semantic relevance.

### WebSockets for chat, HTTP for telemetry

**Chat via WebSocket (`/chat`):** A persistent connection eliminates the TCP/TLS handshake overhead per message and allows the backend to stream responses in the future (chunked generation). The JWT token is validated once at connection time via query param `?token=`, avoiding per-message overhead.

**Telemetry via batched HTTP:** Telemetry events don't require ultra-low latency. Sending in batches (up to 50 events, flushed every 30s or on tab close) is more efficient than a parallel WebSocket for analytical data.

### Asynchronous telemetry ingestion

The `POST /collect` endpoint processes persistence asynchronously (`void service.persist()`) to avoid blocking Node.js's event loop under high volume. The HTTP 201 response is immediate; the database write happens in the background. In production, this would be backed by a queue (Bull/Redis or SQS) for delivery guarantees.

### Two-step signup (signup/start + signup/verify)

The signup flow sends a 6-digit numeric code by e-mail before creating the account. This serves two purposes:

1. **E-mail ownership verification** without depending on external SMS services.
2. **Telemetry signal** — the time between `signup/start` and `signup/verify` is a meaningful behavioral data point.

### Custom CAPTCHA

A simple math challenge (e.g. "What is 7 + 4?") is generated server-side with a configurable TTL. This eliminates dependency on reCAPTCHA/hCaptcha (which carry privacy implications and can be accessibility barriers), while keeping basic protection against automated bots.

### Monorepo with npm workspaces + shared contracts

```
/
├── backend/          @handtalk-challenge/backend
├── frontend/         @handtalk-challenge/frontend
├── packages/
│   └── contracts/    @accessibility-platform/contracts  ← shared types
└── e2e/              @handtalk-challenge/e2e
```

The `contracts` package defines TypeScript types for DTOs and responses in one place. Backend and frontend import from the same package, so contract changes cause type errors on both sides at build time — the equivalent of a Protobuf/OpenAPI schema without the code generation complexity.

### Infrastructure: K3s on Oracle Cloud (Always Free)

The Oracle Cloud Free Tier instance (4 OCPUs, 24 GB RAM, ARM) runs a K3s single-node cluster with:

- **Traefik v3** as ingress controller (bundled with K3s)
- **cert-manager v1.17** with ClusterIssuer Let's Encrypt HTTP-01
- **sslip.io** for free wildcard DNS (`*.157-151-29-59.sslip.io` → `157.151.29.59`)
- **firewalld / nftables** configured to allow pod-to-pod traffic via K3s restart

## 5. Telemetry Strategy

Event curation was designed to cover three analytical dimensions with direct value for AI model training and accessibility research:

### Session and authentication

| Event | Metadata | Analytical value |
|---|---|---|
| `session_started` | `method: password\|signup\|google` | Auth preference by segment |
| `session_ended` | `trigger: logout\|tab_close` | Real session duration |
| `login_succeeded` | `emailDomain`, `provider` | Conversion rate by channel |
| `login_failed` | `reason`, `provider` | Onboarding friction |
| `signup_succeeded` | `emailDomain`, `deliveryMode` | Signup funnel |
| `signup_failed` | `reason` | Signup abandonment |

### Message composition (AI training data)

| Event | Metadata | Analytical value |
|---|---|---|
| `message_started` | `length` | Engagement moment |
| `message_edited` | `length` | Revision frequency |
| `message_cleared` | `previousLength` | Hesitation / abandonment |
| `message_abandoned` | `length`, `trigger` | Uncompleted intent |
| `message_sent` | `length`, `language` | Volume and language of use |
| `typing_pause_detected` | `length`, `pauseMs: 3000` | Cognitive hesitation during formulation |
| `repeated_backspace_burst` | `count` | Intense revision — possible difficulty expressing intent |
| `focus_loss_detected` | `length` | Distraction or context switch |

### Product quality and accessibility signals

| Event | Metadata | Analytical value |
|---|---|---|
| `answer_received` | `mode`, `sources` | RAG quality (grounded vs fallback) |
| `request_latency_observed` | `latencyMs`, `mode` | User-perceived performance |
| `retry_triggered` | `reason` | Failures and resilience |
| `language_changed` | `language` | Language distribution |
| `keyboard_navigation_detected` | `key` | Users relying on keyboard (accessibility signal) |
| `high_contrast_mode_enabled` | `source` | Users needing high contrast |

### Batching architecture

```
┌─────────────────────────────────────────────────┐
│              useTelemetryBatch                   │
│                                                  │
│  events  ──▶  queue[]  ──▶  flush()  ──▶  POST /collect  │
│                                                  │
│  Flush triggers:                                 │
│  • Timer: every 30s                              │
│  • visibilitychange: tab goes to background      │
│  • beforeunload: tab close                       │
│  • Explicit logout                               │
│  • Queue full (50 events)                        │
└─────────────────────────────────────────────────┘
```

## 7. Creative Extras

### RAG (Retrieval-Augmented Generation)

Instead of mocked responses, the chatbot uses a complete pipeline:

1. **Ingestion**: standard documents are split into chunks and stored with vector embeddings (`POST /ingest`).
2. **Semantic search**: the question is embedded and compared against chunks via cosine similarity + pgvector.
3. **Hybrid ranking**: retrieved chunks are re-ranked combining BM25 (lexical) and cosine (semantic) scores.
4. **Grounded generation**: the LLM receives only the top-k chunks as context, forcing answers based on real sources.
5. **Graceful fallback**: if no chunk is relevant enough, the system responds in `fallback` mode and indicates which sources it should have found.

### Google OAuth 2.0

Google login via popup without third-party libraries:
- Frontend opens an OAuth popup with `window.open()` and awaits a `postMessage` with the authorization code.
- Backend exchanges the code via the Google OAuth 2.0 API, validates the `id_token`, creates or retrieves the user, and returns an AccessChat JWT.
- The `client_secret` never leaves the server.

### WhatsApp Integration (Twilio / Meta Cloud API)

[![Falar com o Assistente no WhatsApp](https://img.shields.io/badge/Abrir_conversa_no_WhatsApp-25D366?style=for-the-badge&logo=whatsapp&logoColor=white)](https://wa.me/14155238886)

The accessibility assistant is available on WhatsApp at **+1 (415) 523-8886**:
- Webhook at `POST /whatsapp/webhook` receives messages from the Twilio / Meta Cloud API.
- The service guides users through a conversational authentication flow (e-mail + 6-digit verification code).
- Once authenticated, every message is processed by the same `RagService.answer()` as the web chat.
- Greetings (e.g. "Oi", "Hello") are intercepted before the RAG call and get a friendly reply.
- When no chunk matches the query, a helpful rephrasing prompt is returned instead of the raw fallback message.
- Responses are sent back via the Twilio Messages API with text-friendly formatting.

### Multilingual support (pt / en / es)

The entire interface and RAG prompts adapt dynamically to the selected language. The `language_changed` event is tracked for usage distribution analysis.

### Custom CAPTCHA without third parties

Math challenge generated server-side with configurable TTL — no reCAPTCHA/hCaptcha dependency, preserving privacy and accessibility for users who struggle with image-based CAPTCHAs.

## 9. Running Locally

### Prerequisites

- Node.js 22+
- Docker and Docker Compose
- PostgreSQL with pgvector (via Docker)

### Setup

```bash
# 1. Clone the repository
git clone https://github.com/your-username/accessibility-chat-project.git
cd accessibility-chat-project

# 2. Install dependencies (all workspaces)
npm install

# 3. Create the environment file
cp .env.example .env
# Edit .env with your keys: JWT_SECRET, LLM_API_KEY, etc.

# 4. Start PostgreSQL
docker compose up -d postgres

# 5. Start the backend
npm run dev:backend

# 6. Start the frontend (in a separate terminal)
npm run dev:frontend
```

Frontend will be at `http://localhost:3000` and backend at `http://localhost:3001`.

### Full Docker Compose

```bash
docker compose up -d
```

This starts PostgreSQL, backend, and frontend together.

### Initial knowledge base ingestion

After logging in to the frontend:

1. Open the settings menu (☰ icon).
2. Click **Sync sources** — seeds accessibility standard metadata.
3. Click **Ingest chunks** — embeds and indexes the content.

Or via API:
```bash
TOKEN="your-jwt-here"

curl -X POST https://api-accesschat.157-151-29-59.sslip.io/sources/sync \
  -H "Authorization: Bearer $TOKEN"

curl -X POST https://api-accesschat.157-151-29-59.sslip.io/ingest \
```
